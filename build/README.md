# build/ — packaging resources and the signing story

What lives here:

| file | what it is |
| --- | --- |
| `icon.png`, `icon.icns` | generated by `scripts/make-icon.mjs` (a drawn rounded tile with the `>_` prompt glyph; regenerated on every `npm run dist`, not checked in) |
| `entitlements.mac.plist` | the hardened-runtime entitlements, ported from the reference's `build/azure-pipelines/darwin/app-entitlements.plist` (JIT, audio, camera, Apple Events) |

The bundle recipe itself is `electron-builder.config.cjs` at the repo root.

## What this pipeline does (no certificate)

`npm run dist` builds a **production** (minified) bundle, generates the icon, and runs
electron-builder for `dmg` + `zip`. The **ad-hoc signature** is applied by electron-builder's
`afterPack` hook (in `electron-builder.config.cjs`) — before the dmg/zip are packed, so the zip
electron-updater downloads carries the same signature as the installed app:

```bash
codesign --deep --force --sign - --timestamp=none <app>
```

Ad-hoc signatures are enough to launch locally and to exercise the update loop on this machine.
They are **not** enough to ship: Gatekeeper refuses ad-hoc apps downloaded from the internet
(locally copied apps are fine — `ditto`/`cp` do not add the quarantine flag, browsers do).

## The real signing path (when a Developer ID exists)

This mirrors what the reference's `build/darwin/sign.ts` + `build/azure-pipelines/darwin/`
automate:

1. **Get a Developer ID Application certificate** and put it in the login keychain.
2. **Stop skipping the identity**: remove `mac.identity: null` from
   `electron-builder.config.cjs` (electron-builder then signs every nested binary with
   `--options runtime` — hardened runtime ON).
3. **Turn hardened runtime on**: `mac.hardenedRuntime: true` and keep
   `mac.entitlements`/`entitlementsInherit` pointing at `build/entitlements.mac.plist`. The
   entitlements only take effect under a real signature; with `hardenedRuntime: false` they are
   inert (that pairing is deliberate here).
4. **Notarize** the artifacts (`notarytool` — the reference's pipeline does the equivalent):
   ```bash
   xcrun notarytool submit dist/0varflex-<version>-arm64.zip \
       --apple-id <id> --team-id <TEAMID> --password <app-specific-password> --wait
   xcrun stapler staple dist/mac-arm64/0varflex.app
   ```
   Only the zip needs notarizing for the updater; staple the .app too for first launches.
5. **Verify**: `codesign --verify --deep --strict -vvv dist/mac-arm64/0varflex.app` and
   `spctl --assess --type execute dist/mac-arm64/0varflex.app`.

## Testing the update loop locally

electron-updater **refuses to update a dev run**: the loop must be exercised on the installed
.app.

```bash
npm run dist                          # builds 1.0.0 (or whatever product.json says)
ditto dist/mac-arm64/0varflex.app /Applications/0varflex.app
open -a /Applications/0varflex.app # the installed copy to update

# now make the next version:
#   bump "version" in product.json (and package.json)
node scripts/updates-server.mjs       # serves dist/ on http://localhost:8123
npm run dist                          # dist/ now holds 1.0.1 + latest-mac.yml
```

The installed 1.0.0 checks `http://localhost:8123` (from `Resources/app-update.yml`), shows the
update notification, downloads the zip, and `Restart to Update` swaps the bundle and relaunches.

### The ad-hoc install fallback (why "Restart" installs the zip, not Squirrel's)

Squirrel.Mac validates the downloaded app against a code requirement derived from the **currently
running** app. For an ad-hoc signature that requirement is the app's own cdhash — no rebuilt
bundle can ever satisfy it, so the native installer rejects every ad-hoc update with
`code failed to satisfy specified code requirement(s)`. `src/main/update/updateService.ts`
detects an ad-hoc signature at startup and, instead of `quitAndInstall`, installs the
already-downloaded zip locally: a detached script waits for the app to exit, replaces the bundle
with `ditto`, and relaunches with the original argv. The user-visible flow (toast → Restart →
quit → update → relaunch) is identical; a Developer-ID-signed build takes the normal
`quitAndInstall` path automatically.

Feed URL: `electron-builder.config.cjs` → `publish.url`. Point it at any static directory (the
generic provider is exactly "a static server"; the reference's real feed is a CDN serving
`latest-mac.yml`).

## Notes

- electron-builder downloads the Electron zip per version. On networks where GitHub's CDN
  throttles, `scripts/dist.mjs` sets `ELECTRON_MIRROR` to a mirror prefix whose URL hashes into
  the already-populated cache — a cache hit instead of a download.
- `asarUnpack` in the config is load-bearing: the extension host, the pty host and the toy
  language server are all *spawned*, and `exec` cannot read from inside an asar.
- node-pty is the exception that must NOT live under `app.asar.unpacked`: it rewrites
  `app.asar` → `app.asar.unpacked` in its own spawn-helper path, which corrupts a path that
  already contains `app.asar.unpacked`. It ships as an `extraResources` copy at
  `Contents/Resources/node_modules/node-pty`, where the pty host's require resolves it.
- The CLI script (`resources/cli/0varflex`) ships via `extraResources` so it lives at
  `Contents/Resources/cli/0varflex` — a real file the PATH symlink can point at.
