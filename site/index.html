What’s inside

Every subsystem, ported for real

Not a toy drawing of an editor: the same architecture as the real thing, each piece built from the VS Code source and proven with tests and scripted acceptance runs.

Workbench shell

Title bar, activity bar, sidebar, split editor groups, panel and status bar — with draggable sashes, keyboard navigation, and a layout that persists across relaunches.

titlebaractivitysidebareditorpanelstatus

Editor core

A real text model with an undo stack and save points, virtualised line rendering, IME-safe input, selections and multi-group tabs.

Integrated terminal

A separate pty host process owns real shells, with the reference’s flow control (100k pause / 5k resume watermarks), 5 ms batching and xterm tabs.

Language features

LSP as an extension pattern: diagnostics, completions and hover over a JSON-RPC client/server pair, with markers keyed by resource and owner.

Extensions

A utility-process host loads extensions with an activation-event model and a narrow vscode API shim — three samples ship in the box.

Ship it

Packaged with electron-builder as a real .app — dmg + zip, ad-hoc signing, an update loop against a static feed, and a 0varflex CLI that forwards argv to one instance.

Files & workspace

One file channel behind main, a recursive watcher with change coalescing, an explorer tree, workspace folder and layered settings.

Keys & config

A keybinding resolver with chords, weights and when-clauses, plus defaults < user < workspace settings that reload live.

Terminal

A real shell, not a pretend one

The renderer never touches a process. A dedicated pty host is spawned as a utility process, owns every shell through node-pty, and streams data back over a MessagePort — batched into 5 ms frames and flow-controlled exactly like the reference: pause above 100 000 unacknowledged characters, resume below 5 000.

Measured during acceptance: a yes flood produced 605 paired pause/resume events while the editor stayed interactive and RSS settled at 36 MB.

Language features

Diagnostics that point at the code

A toy language ships with a real LSP client and server: squiggles, completion lists and hover cards flow through the provider registry into the editor — the same extension pattern as the real thing, including $/cancelRequest when a request is superseded.

Squiggles are drawn per severity, the problems picker jumps to ranges, and the status bar keeps the count honest.

Architecture

Processes, ports and one honest boundary

The same shape as the editor it miniatures: a privileged main process, an isolated renderer behind a contextIsolation bridge, and real utility processes for the work that should not live in the UI.

FAQ

Fair questions

Is this a VS Code fork?

No. It’s a from-scratch miniature, ported structurally from a local copy of the real source — file by file, constant by constant — but every line here was written for this project.

Why rebuild something that already exists?

Because architecture is only understood by rebuilding it. Each subsystem — IPC, editor, watcher, extension host, LSP, pty — was built, measured and documented with its deltas.

Does it run on Intel Macs?

Today it ships arm64 only; the electron-builder target list makes x64 a one-line change — untested, and said so in the docs.

Can I install extensions from a marketplace?

No marketplace. Three sample extensions ship in the box, gated by the engines.0varflex range — incompatible manifests are skipped, never crash the scanner.

How do updates work?

electron-updater against a generic feed: the app checks a static server, downloads the zip and offers “Restart to Update”. Because local builds are ad-hoc signed, the installer swaps the bundle from the downloaded zip — same flow, documented as a delta.
